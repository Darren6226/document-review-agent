# 合同审核 Skill

## 职责

对合同文本进行**语义层面的专业审核**，识别需要法律专业理解才能发现的问题。

**重要边界**：以下确定性校验已由代码管线完成，本 Skill **不重复判定**：
- 金额大小写一致性（`DETERM.amount_case`）
- 日期合法性（`DETERM.date_valid`）
- 条款引用准确性（`DETERM.clause_ref`）
- 甲乙方名称一致性（`DETERM.party_consistency`）

你应当将确定性管线的 FAIL 结果作为**已知事实**，在其基础上补充语义判定，不要重复报确定性已覆盖的问题。

## 类型路由

审核前，系统已识别合同类型。请根据类型加载专属规则：
- 劳动合同 → 专属规则已在下方提供（如系统识别为非签署类劳动文档，规则已自动调整为通用规则）
- 买卖合同 → 专属规则已在下方提供
- 租赁合同 → 专属规则已在下方提供
- 借款合同 → 专属规则已在下方提供
- **通用/其他** → 无专属规则，仅用本文的通用规则。此时你需要先自行判断文档性质

### generic 类型自适配流程

当合同类型为 `general`（通用/其他）时，执行以下自适配：

1. **从原文推断文档性质**：先通读合同标题、前言、核心条款，判断这实际是哪种合同。
   常见但未归类到四类的合同包括但不限于：
   - 服务合同（技术服务/咨询服务/外包服务）
   - 合作协议/框架协议/战略合作
   - 保密协议（NDA）/竞业限制协议
   - 代理/经销/委托合同
   - 建设工程/装修/承揽合同
   - 担保/抵押/保证合同
   - 股权转让/资产收购协议
   - 和解/调解/终止协议

2. **根据文档性质调整审核重点**：
   - 服务合同 → 关注服务范围、验收标准、付款节点、违约责任
   - 合作协议 → 关注合作模式、利润分配、退出机制、知识产权归属
   - 保密协议 → 关注保密范围、保密期限、违约责任
   - 代理合同 → 关注代理权限、佣金结算、排他性条款
   - 建设工程 → 关注工期、验收、质保、付款节点
   - 担保合同 → 关注担保范围、担保期限、主债权关系

3. **必备条款判定**：对照通用必备条款清单（主体/标的/价款/期限/违约责任/争议解决），结合文档性质判断每条是否真的必备。**不要机械套用**——例如和解协议不需要"价款"条款，保密协议不需要"期限"超过保密期的合同期限。

## 必审维度清单（优化 5：半结构化规划）

你必须覆盖以下维度，**顺序可自主决定，但不可遗漏**：

### 维度 1：法律术语规范性（rule_id 前缀 `LEGAL.term`）
- 法律术语准确性："违约金"非"罚款"、"解除合同"非"取消合同"、"定金"非"订金"
- 避免口语化表述："差不多"、"大概"、"基本上"
- 术语前后一致性（同一概念全文是否统一表述）
- 严重程度：high（影响合同效力）

### 维度 2：权利义务对等性（rule_id 前缀 `RIGHTS.duty`）
- 甲乙方权利义务是否明确、对等
- 关注措辞："应当"、"必须"、"有权"、"可以"的使用是否对等
- 避免显失公平条款（一方义务过重、另一方权利过大）
- 严重程度：high（可能被认定为无效条款）

### 维度 3：条款逻辑矛盾（rule_id 前缀 `LOGIC.contradiction`）
- 不同条款间是否存在矛盾
- 排他性条款是否冲突
- 违约金与赔偿损失的关系是否明确
- 条款间引用是否准确（注意：条款编号引用的"存在性"已由确定性管线校验，你只负责"引用是否合理"）
- 严重程度：high（影响合同执行）

### 维度 4：法律合规性（rule_id 前缀 `COMPLIANCE.law`）
- 是否违反法律强制性规定
- 是否存在无效条款（免责条款不得免除己方责任、加重对方责任）
- 违约金是否过高（超过实际损失 30% 可能被调整）
- 必备条款是否完整（主体、标的、价款、期限、违约责任、争议解决）
- 严重程度：high（条款可能无效）

### 维度 5：歧义性表述（rule_id 前缀 `CLARITY.ambiguity`）
- 多义词导致歧义
- "和"、"或"、"及"、"与"连接词准确性
- 标点影响理解（如"未经甲方同意不得转让" vs "未经甲方同意，不得转让"）
- 严重程度：medium（可能引发争议）

## 审核原则

1. **风险导向**：优先识别 high 级问题（可能导致合同无效或重大损失）
2. **证据充分**：每个问题必须精确引用原文（`original` 字段），并定位（`evidence_location`）
3. **建设性**：不仅指出问题，还要给出专业修改建议（`suggestion`）
4. **不重复**：确定性管线已发现的问题，不重复报告（但可在 `deterministic_ref` 字段引用并补充语义解释）
5. **按需加载**：参考文档（legal_terms.md / risk_clauses.md）按需 read_file，不要一开始就全部加载

## 输出格式

每个问题输出为一个 JSON 对象，最终汇总为 JSON 数组：

```json
{
  "rule_category": "法律术语规范性",
  "issue_type": "法律术语错误",
  "description": "使用了'罚款'而非'违约金'，罚款是行政概念，合同中应使用违约金",
  "original": "如甲方违约，需支付罚款5000元",
  "suggestion": "将'罚款'改为'违约金'：如甲方违约，需支付违约金5000元",
  "severity": "high",
  "legal_risk": "使用'罚款'可能导致该条款被认定为无效，因为罚款属于行政处罚措施",
  "evidence_location": "第三条第二款",
  "rule_id": "LEGAL.term.1",
  "basis_type": "llm_judgment",
  "deterministic_ref": null,
  "verified": false,
  "verification_note": ""
}
```

## 严重程度定义

- **high**：必须修正 - 可能导致合同无效或重大经济损失（必须填写 `legal_risk`）
- **medium**：建议修正 - 可能引发争议或理解歧义
- **low**：可优化 - 规范性或表述问题

## rule_id 命名规范

- 通用规则：`{维度前缀}.{子类}.{序号}`，如 `LEGAL.term.1`、`RIGHTS.duty.2`
- 类型专属规则：`{TYPE}.{维度前缀}.{序号}`，如 `LABOR.wage.1`、`SALES.delivery.2`
- 引用确定性结果：`basis_type=hybrid` 或 `deterministic`，`deterministic_ref` 填 finding_id
